# Исправления по аудиту 31.10.2026

Ветка: `fix/audit-2026-10-31`. Рабочие данные при подготовке изменений не менялись.

## Поведение после изменения

- Повторная регистрация не входит в существующий кабинет и не перезаписывает его дату рождения, имя или статус. Для существующего телефона нужен обычный вход.
- Клиент определяется по подписанной HttpOnly cookie. Параметр `client` в старой ссылке и `clientToken` из формы/JSON не авторизуют запрос. Срок cookie проверяется сервером — 30 дней для клиента и 7 дней для мастера.
- Пароль мастера хранится как scrypt-хеш с индивидуальной солью. Существующий пароль продолжит работать: сохранённый открытый текст обновится при успешном входе. Смена пароля меняет версию сессии и отзывает прежние cookie; устройство, меняющее пароль, получает новую сессию.
- Попытки входа и регистрации ограничиваются через существующую таблицу `Setting`, с общей блокировкой PostgreSQL. Есть ограничения по адресу, телефону и общий предел. Телефоны и адреса не сохраняются в ключах — используется HMAC. Корректная настройка доверенных proxy-заголовков всё равно важна.
- Все пути создания, редактирования, восстановления статуса записи, публикации окон и изменения перерывов используют одну транзакционную блокировку PostgreSQL. Проверка занятости и сохранение выполняются внутри неё. Вне приложения прямые SQL-записи этим соглашением не защищены.
- Перенос клиента сначала проверяет и создаёт новую заявку, затем отменяет прежнюю запись в той же транзакции. При ошибке старая запись остаётся. При двух одновременных переносах одной записи проходит один.
- Окна подбираются под длительность выбранной услуги, с учётом приёмов, перерывов и конца рабочего дня. Сервер проверяет эти условия повторно.
- Сохранение окон дня целиком откатывается при ошибке. Даты и время проверяются до удаления. Открытие окон в выходной требует сначала отметить день рабочим.
- Объединение клиентов требует выбора найденного дубликата; перенос связей, удаление дубликата и сохранение карточки атомарны. Добавление существующего телефона не переписывает карточку.
- Календарь использует границы месяца во Владивостоке, показывает приёмы и перерывы дня и ведёт в ручную запись с выбранной датой/временем. Есть предупреждение о несохранённых окнах.
- Главная сохраняет начавшийся приём, считает полные объёмы заявок/ожиданий и даёт ссылки на полные списки. Записи имеют фильтры и страницы; лист ожидания имеет собственную страницу.
- Меню мастера доступно на внутренних страницах; архив и чёрный список доступны из настроек. Список клиентов раскрыт сразу. В ручной записи есть поиск и подстановка цены/длительности услуги.
- Обычная отмена формы больше не вызывает подтверждение отмены приёма. Жест обновления отключён на экранах с формами и черновиками.
- Контакты мастера на главной и экране ожидания берутся из профиля. Добавлены фото из галереи, место приёма и действие проверки статуса заявки.
- Next.js обновлён до 16.4.3, React до 19.3.1, среда — Node.js 24.22.1. Асинхронные API Next.js и `proxy.ts` адаптированы. Зависимости зафиксированы lock-файлом; добавлены lint, регрессионные тесты и CI.

При первом выпуске потребуется один раз войти заново: старые cookie намеренно не принимаются. Вход по телефону и дате рождения остаётся текущим способом проверки клиента; подтверждение владения телефоном через код — отдельное продуктовое изменение с выбором провайдера.

## Проверки

```sh
npm ci
npm run prisma:generate
npm run lint
npm run typecheck
npm run test:buttons
npm run test
npm audit --omit=dev --audit-level=moderate
npm run build
```

Без `TEST_DATABASE_URL` выполняются проверки доступа, cookie, хеширования, ограничения попыток, доступности интервалов и бизнес-дат; suite PostgreSQL явно пропускается.

Для транзакционных тестов нужна **отдельная локальная** PostgreSQL с базой `onlinepen_test`. Тесты удаляют только её фикстуры и отказываются работать с любым другим именем базы или нелокальным адресом. `TEST_DATABASE_URL` не должен указывать на рабочую базу.

```sh
export TEST_DATABASE_URL='postgresql://postgres:postgres@localhost:5432/onlinepen_test?schema=public'
DATABASE_URL="$TEST_DATABASE_URL" npm run db:deploy
npm run test
```

CI поднимает собственную PostgreSQL 17. Проверяются конкурирующие ручные/онлайн-записи и восстановления статуса, перенос с ошибкой и два одновременных переноса, принадлежность записи клиенту, отказ вставки окон, отказ финального обновления при объединении карточек, отзыв сессии после смены пароля, сохранность существующего клиента при регистрации, постоянное ограничение попыток и доступность новых записей после 101 исторической.

## Выпуск и база

Обычный запуск Amvera теперь выполняет `npm run start`, без изменения схемы при каждом рестарте. Ветка не требует новых моделей/колонок: новые настройки находятся в имеющейся таблице `Setting`.

Добавлена исходная миграция `20261031000000_baseline`, описывающая существующую схему. Её нельзя просто запускать на заполненной базе с уже существующими таблицами.

Перед включением Prisma Migrate для существующей базы:

1. Проверить резервную копию и восстановление в отдельную базу.
2. Проверить текущую историю миграций и отсутствие расхождений со схемой. Если есть прежняя история или расхождения, сначала согласовать их, не применять baseline вслепую.
3. Если схема полностью совпадает и история миграций ещё не ведётся, отметить исходную миграцию применённой:

   ```sh
   npx prisma migrate resolve --applied 20261031000000_baseline
   npx prisma migrate status
   ```

4. Для следующих изменений схемы использовать проверенные миграции и отдельный этап `npm run db:deploy` перед выпуском. Не использовать `migrate reset`, `--accept-data-loss` или повторное создание рабочей базы.

Для новой пустой базы `npm run db:deploy` применяет исходную миграцию. Перед выпуском проверить поддержку Node.js 24.22.1 на выбранном тарифе/образе Amvera и соответствие переменных окружения. `ADMIN_SECRET` и `CLIENT_SESSION_SECRET` должны быть стойкими случайными значениями длиной не менее 32 символов, не содержимым этого документа. Пароль мастера больше не используется как ключ подписи cookie.

Проверки состояния:

- `/api/health/live` — процесс приложения отвечает;
- `/api/health/ready` — доступны таблицы приложения и корректно заданы ключи сессий; возвращает 503 при ошибке.

Смена версии приложения и бэкапы хостинга остаются отдельными операциями. В этой ветке нет команд удаления данных или автоматического переноса инфраструктуры.
